Packed Flexmap Benchmark

flexmap branch packed-index against origin/zeroable_load (cebfd56, the rev flexalign pins). The packed index holds the same k-mer positions and flank cells in less memory and answers every lookup with the same seeds. Quick runs: 2 M queries per dataset and scenario, one timed round after a warm-up.

At a glance

Short reads, one lookup call per 150 bp read, M seed lookups per second, both sides with their batch prefetch. Memory is the whole index in RAM.

What was changed, and what was tried

  • Packed values. A value takes ref_bits + pos_bits (17 + 24 = 41 bits at D1), not 64; flank cells stay 32-bit and byte-aligned so the flank scan reads plain integers; every value can be read on its own; the key table's offsets are unchanged.
  • Compact key table. A presence bit per key (448 keys and a rank count per 64-byte line) and a 24-bit start per used key, instead of a 16-bit cell for every one of the 415 keys (2.68 GB). A hit reads two lines, one after the other.
  • Hashed key table (added after the first results). The used keys in a table of 64-byte lines, 8 entries a line at load ≤ 0.75, so a hit reads one line; 10.7 bytes a used key. A bit per line marks that keys homed there overflowed, so most misses read one line (random-key lookups 17 → 27 M/s at D1 with it); misses still cost more than in the compact table. Built from the compact file in 0.5 s, sharing its values. Its line count is any number (a key's home line is key × lines / 415), not a power of two: D3's 50.43 M used keys took 1.07 GB of lines as a power of two and take 0.54 GB now (same lookups, 3.61 → 3.51 M/s per read at the lower load).
  • Prefetch pipeline. The key table 24 lookups ahead, a compact table's start 16 ahead, the values 8 ahead. The old blob prefetches the key block 24 ahead only, which never starts inside a 150 bp read (~24 k-mers); the packed pipeline still overlaps a read's own lookups.
  • Huge pages (madvise) for the large arrays, also in the old blob's loader: 1.2–1.4× for the old blob alone. FLEXMAP_THP=0 turns them off (the baseline rows).
  • Parallel load of the packed file into a huge-page buffer; mmap is also offered.
  • Two FMKeys fixes: the occurrence count saturates instead of wrapping at 65,536, and a key whose cells would pass its block's 16-bit offset is left out instead of corrupting the block.
  • Tried, no gain on D2 (table below): a one-pass flank scan, prefetching 16 or 32 value lines instead of 8, prefetch steps of 4 or 12, and a faster value decoder. D2 is bound by emitting its ~150 seeds a lookup (about 7 ns each in the consumer), which every variant pays alike.

Setup

  • Index as flexalign builds it: K 31, C 15, F 16, closed syncmer S 4, 16 keys per block, header threshold 2, keys over 2,048 values left out.
  • Queries are the true k-mers of contiguous sequence: reads drawn from the reference (random strand, 1% substitutions); every syncmer k-mer of a read, in read order, is a query, with its key and flank as the build makes them. Per read: one lookup call per read, as an aligner takes a read at a time. Stream: all reads' k-mers in one call per thread. Random keys: uniform over 230.
  • The consumer hashes every emitted seed (position, reference, distance, ties) into a per-query checksum; the sums are compared across variants. The unit tests compare every key of a test index field by field.
  • Indexes on /dev/shm (RAM) or on SSD (D1 and D3 hashed), so load times are mostly memory speed. Each variant runs in its own process; threads take contiguous parts of the reads.
  • Machine: Intel Core i9-13900HX (AVX2, no AVX-512), 12 logical CPUs, 31 GB RAM shared with other work, Linux 6.17, rustc nightly 1.99. Some loads ran under memory pressure, so load times vary; runs that swapped during lookups were repeated.
